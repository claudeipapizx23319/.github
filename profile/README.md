<p>长连接这个词，在代理选型里被用得有点滥。有人指的是 SSE 流式输出不要断，有人指的是 WebSocket 能不能穿过去，还有人只是想让脚本复用 TCP 连接少握手几次。这三种需求对线路的要求完全不同，用同一套标准去挑，钱花了问题还在。下面按决策清单的写法，先做三道判断题，再按四组检查项逐条过，每组给出可验证的动作，最后落到观测和兜底。</p>

<h2>一、先过三道判断题，决定要不要长连接</h2>
<p>不是所有场景都需要长连接。先用三个问题筛一遍，能筛掉一大半无效需求。</p>
<h3>连接是持续存在还是用完即弃</h3>
<p>流式对话、WebSocket 推送、数据库连接池，属于持续存在，一次连接存活几分钟到几小时。普通的页面抓取、接口查询，属于用完即弃，一次请求几秒钟。前者对空闲超时和保活敏感，后者更在意建连速度和并发数。这两种需求不要放在同一条线路上评估。</p>
<h3>断了之后能不能重来</h3>
<p>能无痛重来的，比如拉取一篇文章，断线只是慢一点；不能重来的，比如已经输出了八百字的长回答，断了就得重新生成，成本和体验都受损。判断标准是"重试一次的代价"，代价高的才值得为长连接多付钱。</p>
<h3>客户端能不能改配置</h3>
<p>有些客户端把超时写死了，改不了；有些支持自定义 keepalive 参数。改不了配置的，就只能靠线路侧撑住；能改的，优先在客户端调，成本更低。这条经常被忽略，结果是在线路侧折腾半天，其实改一行配置就解决了。</p>

<h2>二、清单第一组：协议和端口撑不撑得住</h2>
<p>协议决定了连接能不能长期存在，端口决定了连接能不能建立。两件事都要过。</p>
<h3>HTTP/1.1、HTTP/2 与 WebSocket</h3>
<p>HTTP/1.1 的 keep-alive 是复用，不是长连接语义，服务端随时可以关。HTTP/2 多路复用，一条 TCP 上跑多个流，对并发友好，但对中间代理的实现要求高，部分代理会把流拆开导致头部阻塞。WebSocket 需要代理支持协议升级（Upgrade），普通 HTTP 代理默认不转，得用支持 CONNECT 的隧道模式。买之前问清楚"是否支持 CONNECT 隧道"，这一句能省掉很多试错。</p>
<h3>空闲超时是哪一端设的</h3>
<p>连接断掉，可能是客户端超时、代理超时、也可能是目标站超时。三层都要查。经验值：代理侧空闲超时常见 60 秒、120 秒、300 秒；目标站侧对流式接口一般在 60 到 90 秒无数据就断。如果你的心跳间隔大于最短的那个超时，连接必然被回收，现象是"每隔一分钟断一次"。</p>

<h2>三、清单第二组：心跳与会话保持参数</h2>
<p>心跳不是越勤越好。太勤会增加无效流量，太疏会被超时回收。目标是让间隔小于链路上最短的空闲超时，同时留出一次重试的余量。</p>
<h3>心跳间隔怎么取</h3>
<p>先测出最短超时：在空闲状态下打一条命令观察多久断，<code>curl -x http://用户:密码@地址:端口 -v https://目标域名</code>，看返回头里的 <code>Keep-Alive: timeout=xx</code>，没有这个头就用抓包看断开时间。取这个值的三分之一作为心跳间隔，60 秒超时对应 20 秒心跳，300 秒对应 100 秒。TCP 层可以开 <code>SO_KEEPALIVE</code>，Linux 下用 <code>net.ipv4.tcp_keepalive_time</code> 调，默认 7200 秒太长，改成 120 秒更实际。</p>
<h3>应用层心跳和传输层心跳别混</h3>
<p>TCP keepalive 只能探活，不能证明应用还能处理请求。应用层心跳（比如发一个轻量请求）才能确认端到端可用。两层都开是常见做法：传输层负责发现死链，应用层负责发现"连得上但没响应"。代价是流量略增，一条连接一天几 MB，一般可接受。</p>

<h2>四、清单第三组：断线之后怎么接回来</h2>
<p>长连接一定会断，问题是怎么断得可恢复。这一组是能不能上生产的分水岭。</p>
<h3>重连要带退避和抖动</h3>
<p>固定间隔重连会在服务端故障时形成尖峰。做法是退避：1 秒、2 秒、4 秒、8 秒，上限 60 秒；再加 0 到 30% 的随机抖动，避免所有客户端同时重连。连续失败十次后转告警，别无限重试。</p>
<h3>断点续传靠什么</h3>
<p>SSE 用 <code>Last-Event-ID</code>，客户端重连时带上最后收到的事件 ID，服务端从该点续发。WebSocket 没有标准机制，要自己在协议里加序号和补偿拉取。都不支持的，只能在业务层做幂等，把"重来一次"的代价压到最低，比如缓存已生成内容、按段落校验完整性。</p>
<h2>五、清单第四组：观测与兜底</h2>
<h3>四个必看指标</h3>
<p>连接建立成功率、平均连接存活时长、单位时间重连次数、首包延迟。前两个看线路质量，后两个看稳定性。连接存活时长如果集中在某个固定值附近，比如都是 60 秒，那基本可以断定是某一端的空闲超时，而不是网络抖动。首包延迟突然抬升，往往意味着出口拥塞或路由变化。</p>
<h3>备用线路怎么切</h3>
<p>至少两条不同运营商的线路，主备切换用健康检查驱动，检查间隔 10 秒、连续三次失败切换。切换后保持原会话的令牌和配置不变，只换出口地址。注意切换不要过于频繁，加一个"切换后 5 分钟内不再切回"的冷却，否则会在两条都不稳的线路上来回弹。</p>

<h2>常见问答</h2>
<h3>住宅代理支持 WebSocket 吗？</h3>
<p>答：看实现。走 HTTP CONNECT 隧道的住宅代理一般可以，因为它只转发 TCP 字节流，不解析内容。只做 HTTP 转发、不支持 CONNECT 的不行，握手阶段就会失败。买前用 wss 测试页跑一遍最直接。</p>
<h3>长连接会不会更容易被判定异常？</h3>
<p>答：连接时长本身不是判定依据，行为才是。长期挂一条连接但没有任何交互，反而更像异常。正常使用下的长连接（流式输出、持续对话）属于产品本身的交互方式，不必刻意缩短。</p>
<h3>心跳间隔设 10 秒是不是更保险？</h3>
<p>答：不一定。心跳太密会增加流量和 CPU 开销，移动网络下还更费电。按最短空闲超时的三分之一取就够，60 秒超时配 20 秒心跳已经留了充足余量。</p>
<h3>一条线路能撑多少长连接？</h3>
<p>答：取决于服务商的端口数和会话数限制，不是带宽。常见单端口支持几十到几百个并发会话，具体看套餐。超过之后表现为新建连接被拒或排队，这时要加线路而不是加带宽。</p>

<h2>合规提示</h2>
<p>长连接配置属于网络工程质量问题，与平台规则无关。使用时应遵守目标平台的服务条款，不利用连接特性进行高频请求、批量操作或其他影响服务正常运行的行为。</p>
<p>代理线路仅用于自有账号、自有业务的网络接入。请勿将线路转售、共享给无关第三方，由此产生的法律责任由使用者承担。</p>
